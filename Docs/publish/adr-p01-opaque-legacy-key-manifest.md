# ADR-P01: The Legacy Period Key Is Opaque — Application Resolves Monthly Identity Via Manifest

## Metadata

| Date | 2026-06-08 |

---

## Context

The legacy payroll monthly tables (`legacy.monthly_salary_lines` and related child tables) use an internal `legacy_period_key` column to identify an employee-period combination. This key was generated by the legacy MS Access system using a rule that may be numeric-only, composite, or string-based — the physical type has not been confirmed from production data.

The new application must be able to:

1. Look up existing monthly rows by employee + period.
2. Write new monthly rows for employees who have no existing legacy row.
3. Link parent and child monthly rows using the correct `legacy_period_key`.

Three strategies were considered:

**Option A — Parse the key**: Reverse-engineer the legacy generation rule and generate `legacy_period_key` values using the same algorithm.

**Option B — Generate new opaque keys**: Ignore the legacy key format and use new UUID or sequence-based keys for all new rows.

**Option C — Application-owned manifest**: Use `payroll_app.period_key_manifest` to track the mapping from `(employeeRef, period)` to `legacy_period_key`. For existing rows, read the key from the legacy table. For new rows, allocate a safe new key. Never parse.

---

## Decision

`legacy_period_key` is treated as **opaque** by all application code.

The application uses `payroll_app.period_key_manifest` as the authoritative mapping from the public identity `(employeeRef + period)` to the internal `legacy_period_key`.

`parseLegacyPeriodKey()` is forbidden. Any call to parse, decode, or derive semantic meaning from a key value must throw an error.

---

## Rationale

**Against option A (parsing):**

1. The physical type and generation rule of the key in production have not been confirmed. Building a parser on unconfirmed assumptions risks generating colliding or invalid keys that corrupt legacy monthly data.
2. Even if the rule is reverse-engineered today, the legacy system may have used exception cases or manual overrides that are not reflected in the general rule.
3. Parsing creates a hidden dependency on an internal implementation detail of the legacy system.

**Against option B (new opaque keys only):**

1. Existing legacy monthly rows already have key values. If the application generates a different key for the same employee-period, it cannot link to the existing parent row.
2. Writing child rows with a different key than the existing parent row would break the legacy join and make the monthly snapshot inconsistent.

**For option C (manifest):**

1. The manifest resolves from existing legacy rows first — using the existing key from `legacy.monthly_salary_lines` where it exists.
2. Only when no legacy parent row exists does the application allocate a new key.
3. Allocation strategy can be decided after physical type confirmation (string UUID vs numeric sequence) without changing the manifest API.
4. `parseLegacyPeriodKey` can be implemented as a permanent hard error, making the constraint explicit and enforceable.

---

## Resolution Algorithm

```text
1. Look up payroll_app.period_key_manifest by (employeeRef, period).
2. If found → use manifest key.
3. If not found → look up legacy.monthly_salary_lines by employee_ref + period_year + period_month.
4. If legacy parent found → insert manifest row (source = legacy-parent-row) → use that key.
5. If no legacy parent → allocate new opaque key → insert manifest row (source = allocated).
6. All monthly writers receive the key from this resolver. They never generate it independently.
```

---

## Open Decision: Allocation Strategy

Before phase 4 is implemented, the physical type of `legacy.monthly_salary_lines.legacy_period_key` must be confirmed against production.

**If numeric-only**: allocation must use a SQL Server sequence or locked numeric allocator. String UUIDs must not be stored in a numeric column.

**If string**: allocation may use opaque string keys (e.g. `calc_<ulid>` or sequence-formatted text).

This decision does not change the manifest architecture — it only affects the allocation implementation.

---

## Consequences

### Positive

- Monthly writes are safe for both employees with existing legacy rows and new employees.
- The application never risks generating a colliding key.
- The manifest provides a queryable audit of every `(employeeRef, period)` → key mapping.
- Allocation strategy can be swapped without changing the manifest API.

### Negative

- Every monthly write path requires a manifest lookup (one extra SQL read).
- The manifest must be populated before any child writer runs.
- Phase 11 (monthly preparation apply) is blocked until Phase 4 (manifest implementation) is complete.

### Constraints Imposed

1. The shared payroll key module must export `resolveOrAllocatePeriodKey(employeeRef, period)`.
2. `parseLegacyPeriodKey()` must throw a `ForbiddenKeyParsingError` — it is never a valid operation.
3. All monthly writer services must call `resolveOrAllocatePeriodKey` — they must not generate the key independently.
4. `payroll_app.period_key_manifest` is unique by `(employee_ref, period)` and by key. Conflicts indicate a bug.
